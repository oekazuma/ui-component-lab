# 設計 016: 各部品の「避けたい使い方」（ディセプティブパターンを含む）

## 目的

UI を選んで作る人（デザイナー、エンジニア、企画者）が、実装前にその部品の誤った使い方を知り、避けられるようにする。

企画者の多くは、良くしようと思って UI を選ぶ。その善意が利用者に害を出す結果にならないようにしたい。害には 2 種類ある。

- だます使い方（ディセプティブパターン、ダークパターン）。利用者が望まない選択をするよう仕向ける。例は、同意のチェックボックスを最初からオンにしておく、解約の操作だけ目立たなくする、など
- 悪意がなくても害が出る使い方。作り手は良かれと思っているが、利用者を困らせる。例は、カルーセルの自動再生

読み終えた人が、その部品を誤った使い方で実装しないことを成功とする。

## やること

- 詳細ページに「避けたい使い方」のセクションを 1 つ足し、2 種類をまとめて載せる
- 1 件ごとに 3 つを書く
  1. どういう使い方か
  2. 誰がどう困るか
  3. 代わりにどうするか
- だます使い方の項目には「ディセプティブパターン」のラベルを付け、用語も覚えられるようにする（設計者の判断）
- 既存の `usage`（使い分け・注意点）にある「〜しない」系の記述のうち、3 つの要素で書けるものは新しいセクションに移す。部品の選び分けや書き方の助言は `usage` に残す
- 全 46 部品を調べ、根拠のある項目が見つかった部品にだけ書く

## やらないこと

- 根拠のない項目を書かない。出典が見つからない項目は、もっともらしくても載せない
- すべての部品に無理に項目を作らない（区切り線やスケルトンなど、見つからない部品は空でよい）
- 法律の解説や、法令に違反するかどうかの判断は書かない
- 一覧ページには出さない（詳細ページだけ）
- 項目での検索や絞り込みは作らない

## 失敗とみなすもの

- 出典が裏付けていない内容や、出典を開かずに書いた内容が載る
- 読み手を責める口調になる。「〜するな」ではなく、困る人と代わりの方法を示す
- 例が抽象的で、実装前の判断に使えない（「わかりにくくしない」など）

## 決まっていること

### データ

`src/lib/types.ts` の `ComponentData` に省略可能なフィールドを足す。

```ts
/** 避けたい使い方。根拠にした資料は sources に載せる */
misuse?: {
	/** どういう使い方か */
	pattern: Text;
	/** 誰がどう困るか */
	harm: Text;
	/** 代わりにどうするか */
	instead: Text;
	/** 利用者をだまして望まない選択に誘導するもの（ディセプティブパターン）なら true */
	deceptive?: true;
}[];
```

- 文言は既存と同じく `{ en, ja }` の両方を書き、同じ内容にする
- 根拠にした資料は既存の `sources` に足す。`checkedAt` は実際に開いて確かめた日にする（CLAUDE.md の約束どおり）。DADS の出典ラベルの約束も同じ
- 文は出典の言い換えで書き、出典の文を写さない

### 表示

- 詳細ページ（`src/routes/[lang=lang]/components/[id]/+page.svelte`）の「使い分け・注意点」の直後に置く。項目がない部品ではセクションごと出さない（`usage` と同じ扱い）
- 見出し: 日本語「避けたい使い方」、英語「Misuses to avoid」（設計者の判断）
- 3 つの要素には、それぞれ短いラベルを付ける。日本語「困ること」「代わりに」、英語「Harm」「Instead」。使い方の本文は項目の見出しにする（設計者の判断）
- `deceptive` の項目には「ディセプティブパターン」「Deceptive pattern」のラベルを付ける。色は既存トークンで足り、色だけで区別しない（文字のラベルを付ける）

### 検査

- `src/lib/data.check.ts` の重複キー検査に `misuse`（`pattern.en`）を、空文字検査に 3 つの `Text` を足す
- CLAUDE.md の「data.ts」の節に、`misuse` の書き方（3 つの要素、`deceptive` の付け方、出典）を足す

### 根拠の基準

- 部品を問わない資料を、部品に当てはめて書いてよい。例: deceptive.design の類型「Preselection」をチェックボックスとスイッチに当てはめる、WCAG 2.2.2（一時停止、停止、非表示）をカルーセルとトーストに当てはめる
- ただし「誰がどう困るか」（harm）は出典に書かれている内容に限る。その使い方が部品に当てはまるかどうか（pattern）と、代わりの方法（instead）は作る人が判断してよい
- `deceptive: true` は、出典がディセプティブパターンやダークパターンとして分類しているものにだけ付ける（deceptive.design の類型、FTC の報告など）。作る人の判断では付けない（設計者の判断）
- 「実際に開いて確かめた」は、AI エージェントがページを取得して内容を確かめたことでよい。`checkedAt` はその日付にする。マージ前に人が開き直す工程は要らない

### 出典の候補

項目ごとに、裏付けになる資料を実際に開いて確かめる。候補:

- デジタル庁デザインシステム（DADS）の各コンポーネントの使い方のページ。例: カルーセルの自動再生 https://design.digital.go.jp/dads/components/carousel/usage/
- deceptive.design（Harry Brignull によるディセプティブパターンの類型集）の各類型のページ
- WCAG 2.2 の達成基準と、その解説（Understanding）
- WAI-ARIA APG の各パターン
- 各国の規制当局の報告（例: 米国 FTC の 2022 年のスタッフ報告 "Bringing Dark Patterns to Light"）

## 作る人に任せること

- 調べる順番と、作業の分け方（カテゴリごとに分けるなど）
- 1 部品あたりの項目数。目安は 0〜3 件。数より根拠の確かさを優先する
- セクション内のスタイルの細部（既存の詳細ページの見た目に合わせる）
- `usage` から移す記述の線引き（上の基準に沿って判断する）
- テスト: `pnpm check` と `pnpm build && pnpm test:e2e` が通ること。axe の対象に、項目のある詳細ページが少なくとも 1 つ含まれるようにする
